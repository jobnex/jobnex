# Tailor Resume recovery record (2026-10-04)

## Scope

Public flow: `job-hunt-web` → `app/api/resume/tailor/*` → Neon `neondb` → private `job-hunt-resume-worker` → Python résumé agent → Markdown in `resume_generations`. The selected published job `1a8a3167-bf4a-5619-8167-b43d883e83e4` was confirmed in Neon. The separate Rust `ai-job-portal-staging` service is **not** in this public flow. All checks below targeted GCP project `job-scout-508222`, region `us-east1`. No credentials, OTPs, tokens, personal résumé text, or generated content are included here.

## Investigation and changes, in order

1. Read both Cloud Run configurations and tested the private worker `/health` with an identity token. Both web and worker had `RESUME_GENERATION_ENABLED=false`; worker health showed `enabled:false`. Public requests were gated before any credit hold. There were six historical failed generation requests, all with `credit_state=released`, and zero stuck running requests.
2. Enabled only the private worker while keeping the public web gate closed. A disposable synthetic candidate, source résumé, published-job snapshot, and one held test credit were inserted in Neon. Request `15e3edf6-952b-4c88-8979-22d2c875c207` failed with missing `tailored.md`; the credit was refunded.
3. Root cause: `services/resume-tailor/worker.ts` used `python -m low_risk_agent.cli`, whose module defines but never calls `main()`. Changed to `python -m low_risk_agent`; `resume-agent-inspect/src/low_risk_agent/__main__.py` invokes `main()`. A local `--help` check proved the entrypoint starts. Worker image build `45d9123d-e825-41fd-adbd-63d5bba93e22` succeeded and revision `job-hunt-resume-worker-00016-hn7` deployed.
4. Request `d669d84b-0866-48c0-957e-9da59fef741c` reached the agent and saved Markdown, but ended `needs_review` on `claim.weak_verb`; the test credit was returned. A longer job-aligned synthetic source was then used. Request `d7353513-ada8-45eb-ba85-1fafb61a1814` saved Markdown but failed AI-usage accounting because `resume_ai_calls.id` is required without a default. Schema inspection also showed its `status` check accepts `started`, `reported`, or `unknown`, whereas the worker wrote `completed`. The worker now supplies a random UUID and writes `reported`. A superseded image build was cancelled before deployment.
5. A refunded request could still have a completed `resume_generations` row. The generated-Markdown GET route now joins `resume_generation_requests` and requires the same owner, `r.status='completed'`, and `r.credit_state='consumed'`. The new SQL denied both refunded test IDs. `npx tsc --noEmit --pretty false` passed. The installed Next.js Route Handler guide was checked for the endpoint convention.
6. The final worker image `repair-20261004` built in Cloud Build `335f0d26-88b7-4a13-b199-8da49d3d47fa` and deployed as `job-hunt-resume-worker-00017-4qb`. A first retest correctly returned/refunded on `metric.provenance`. The synthetic source was expanded with explicit metrics. Request `6b86c0e8-7057-4a09-a01a-2d7af647f799` then **completed** with persisted Markdown, four `resume_ai_calls` rows, `credit_state=consumed`, and final wallet balance 0.
7. To avoid shipping ten unrelated changes on `main`, the web image was built from the exact previously deployed base commit `b942ac0` plus only these two repairs. Web build `69fdd1ab-86d2-4a0c-944b-707129afdb18` succeeded. It deployed as `job-hunt-web-00011-w5g` with its gate still off, then `job-hunt-web-00012-rjj` with `RESUME_GENERATION_ENABLED=true`. The public selected-job page rendered “Tailor for ProjectWise Administrator” and showed the signed-in candidate upload control. Anonymous `POST /api/resume/tailor/requests` returned 401. The private worker health returned `{"status":"ok","enabled":true}`.

## Boundaries and remaining checks

The database-level worker acceptance test passed, but a complete browser upload → preview → generate → Markdown download was **not** executed against a real candidate account. The browser had a signed-in session and loaded the authoritative job, but no personal résumé was uploaded or real candidate credit spent. A release owner should complete that final user-level check with an explicitly approved test account/file, verify the same request's credit transaction and downloaded Markdown, and monitor error and refund rates after release. Prior provider errors (`provider_http_402`, `provider_outcome_unknown`, daily-token exhaustion) show that provider capacity can still fail; refund behavior was verified for the tested failures.

Rollback: set `RESUME_GENERATION_ENABLED=false` on `job-hunt-web` first so no new credit holds are accepted, let queued work finish/refund, then disable the worker if needed. The previous image tag on both services was `jobnex-pr4-b942ac0`. No schema migration was made.

The fix and this record were published as [PR #8](https://github.com/jobnex/jobnex/pull/8). After the final audit, all five positively identified disposable test requests and only their synthetic résumé, wallet, credit transactions, generated rows, and AI-call rows were removed in one transaction. No real candidate record was deleted. Those test rows are not recoverable through the app; Neon point-in-time restore is the fallback if needed.
